# Phase 3 deployment and live acceptance

No deployment or hosted migration was performed. This is the concrete setup needed to activate the implemented Notes route.

1. Review and apply [`20261020000000_notes_connections`](../../../../prisma/migrations/20261020000000_notes_connections/migration.sql) through Sylf's normal migration process. It adds only broker metadata. Generate the Prisma client for the deployed schema; `SCHEMA_BUILD_VERSION` is 37.
2. Set server-only `NOTES_PUBLIC_URL` to the exact HTTPS Sylf origin. Register `<origin>/api/notes/callback` as the Google web OAuth redirect and enable Drive API in that Google project. Keep this origin/client identity stable. Drive roots are bound to a hash of the canonical origin; changing it requires an explicit verified migration. Use separate authorized test accounts/clients for staging and production. Development loopback HTTP is allowed only outside production.
3. Generate a separate 32-byte base64 `NOTES_ENCRYPTION_KEY`, for example `openssl rand -base64 32`, and store it in the deployment secret manager. Use the same key on every server instance. Securely back it up with database backups containing wrapped vault keys. Do not put it in `NEXT_PUBLIC_*`, Vite variables, logs or client storage. Never replace it without an explicit rewrapping migration.
4. Prefer stable dedicated `GOOGLE_NOTES_CLIENT_ID` / `GOOGLE_NOTES_CLIENT_SECRET`. The broker otherwise uses Sylf's configured `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`; the Notes grant/state/storage remains separate from login and Calendar grants. Changing OAuth applications after provisioning needs migration planning, not an environment-only switch.
5. Configure consent/test users and publication/verification requirements for that application's actual Google Workspace policy. Scope request is `openid email https://www.googleapis.com/auth/drive.file`, with offline consent and PKCE. No school-tenant or production-consent approval is asserted by the local tests.
6. Deploy the web build and publicly accessible source notices generated by `scripts/build/build-notes-notices.mjs`. The normal web/mobile prebuild hooks include this step. Keep `/sw.js`, `/notes-offline.html`, callback and broker endpoints on the intended origin; do not add authenticated response caching.
7. Use an explicitly authorized disposable Google account to run the live checklist below. Export an independent portable copy before any destructive provider test. The local test grants/fixtures must never become production provisioning shortcuts.

At inspection, existing Google OAuth credentials were present, but `NOTES_PUBLIC_URL`, `NOTES_ENCRYPTION_KEY`, dedicated Notes client variables and an authorized Notes Drive test grant were absent. Only presence was inspected; no secret values were printed or changed. Consequently the UI fails closed for unavailable Notes setup rather than simulating provisioning.

## Live acceptance checklist (not performed)

- Sign in with real Sylf cookies; complete actual Google consent, callback state/PKCE, create/read probe and root enrolment. Verify granted scopes and no Calendar credential reuse.
- Create/edit rich text and images, confirm exact provider readback, reconstruct in a clean second browser and compare document/stream/page/revision identities and original image hashes.
- Two independent devices: offline edits, simultaneous text changes, metadata conflicts and deletion/edit conflicts; verify all branches and explicit recovery.
- Interrupt an upload after Google has accepted it; retry without losing or replacing commits. Test Drive quota/throttling and refresh credential races across server instances.
- Revoke Google consent and reconnect the original account. Wrong accounts, missing roots/descriptors, externally moved/removed/corrupt packs and expired list tokens must retain local work and never receive a false cloud-save claim.
- Expire/revoke Sylf sessions and switch users in two browser tabs. Check vault/key closure, no previous-owner body/title/image exposure, blocked explicit logout on storage failure and same-owner recovery.
- Test the actual deployment's body/time/memory limits, CSP/cookies/CORS and browser download behavior. Bounded local HTTP fixtures do not qualify deployment policy.
- Physical Safari/iPad/iPhone, Android browser and intended WebViews: keyboard/composition, touch targets, accessibility, viewport changes, real storage pressure, crash/offline behavior and long documents/histories. A successful Vite build does not qualify native OAuth/CORS/return-to-app or protected storage.

The broker deliberately rejects arbitrary/null/native origins. Production native Notes connectivity remains gated until a reviewed capability-aware authentication/return flow is qualified. Do not relax origin checks to make a WebView test pass. Web responsive layouts and shared mobile compilation are separately verified.

## Product/release choices

The implementation chooses encrypted retained browser data and online cold unlock over an offline authentication bypass. Confirm that policy and the key-backup/rotation runbook before rollout. Confirm user-facing browser durability wording and independent export guidance; do not promise survival of cleared unsynchronized storage. Provider-readable cloud v1 remains provisional; E2EE, OneDrive, retention pruning and stronger native durability require separate approval/design. No additional approval is needed to review the local implementation; deployment and real-provider access are separate actions.
