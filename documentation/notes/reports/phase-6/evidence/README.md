## Baseline and targeted comparisons

- `baseline.json`: hashes of 207 existing source/prior evidence files. No difference from the final Phase 5 snapshot at Phase 6 start. `source-snapshot.json` records final changes and preserved boundaries.
- `history-40-before-final.json` / `history-40-after-final.json`: matched 40-revision encrypted repository fixture with lightweight read counters. The retained before module matched Phase 5's exact source hash. Integrity: 3,360→81 object reads and 1,084.5→27.2 ms. Closure: 161→81 reads; its small-run latency was 28.6→37.4 ms, so no universal latency improvement is claimed. Both retain 81 source objects/37,958 ciphertext bytes. Publication pack counts differ with random immutable IDs; these are not a controlled upload-throughput comparison.
- `packed-120-before.json` / `packed-120-after.json`: same 120-revision / 12-pack layout, 136,061 unique provider bytes. Restore downloads fall from 41 reads/466,220 bytes to 12 reads/136,061 bytes, preserving all native text and revisions. Audit is explicitly skipped in this network-targeted profile. `packed-120-final.json` repeats the final code: same 12 reads/136,061 bytes. Its timing overlapped builds and is not a quiet latency comparison. The initial pair's 640→303 ms is illustrative, not live Drive throughput.
- `resources-before.json` / `resources-after.json`: actual rich-text UI, eight 2 MiB padded valid PNGs, 24 open/close cycles. Retained Blob URLs: 8/16 MiB→0/0; all 24 created URLs revoked after the fix. Main-window heap is essentially unchanged (~15.9 MB after startup/cycles); neither heap reduction nor megapixel decode bounds are claimed. Originals remain encrypted and reopen correctly. `resources-*.log` record process results. `resources-final.json` repeats the final code with the same cleanup assertion.

The final claim-batch addition changes queue selection but not the compared closure/audit or per-pull proof algorithms. Normal saves still require transaction acknowledgement; provider verification still requires hash-checked bytes and readback.

## Retained failed diagnostics

Do not read a log ending in failure as a passing acceptance run:

- Earlier `history-180-before*`, `history-before.log` and `history-1000-*` attempts exceeded time budgets. Initial profiling spies retained every read result; they were replaced by lightweight counters. Even the later 1,000-revision fake-IDB run timed out. `simulator-cpu-summary.json` records roughly 163 of 206 sampled seconds in timer/fake-database transaction scheduling, including repeated scans of retained finished transactions. These runs are not actual browser performance measurements. The completed real Chromium backlog is the relevant result; simulator code was not patched to manufacture a pass.
- The first hardening run exposed an incorrect recovered frontier when a journal row was missing and cursor-loop tracking retained across expiry. Both production issues were fixed; `hardening-tests.log` is the subsequent seven-test passing intermediate run, and `regression.log` adds the atomic lease test for eight final hardening regressions. Initial failure output was observed in tool results, not retained in that overwritten intermediate log.
- `soak-first-outage-onboarding.log` / `soak-first-progress.json` / `independent-first-library.sylfnote`: the first full five-minute writing/reload/audit/export succeeded, but the fresh restore profile was intentionally still offline and correctly refused first-use discovery. The driver now restores provider availability before fresh-profile enrolment; the final completed run is `soak-results.json`. No onboarding/security check was disabled.
- Other unsuffixed early history/resource/build logs are intermediate observations, not substitutes for the final files indexed above. Host timestamps and client date can differ; logs retain actual process times, report date follows the user's 22 October environment.

No evidence establishes physical stylus latency/palm rejection, Safari/Firefox/WebView compatibility, hours/academic-year history, browser-clearing survival, maximum corpus safety budgets, real Drive quotas/latency or a production deployment. Those remain explicit release gates.
