## Validation and ownership boundary

Parse each artifact before using its typed helpers. Objects are strict; unknown fields are rejected, strings normalized by their schemas, civil dates validated and timezones checked. Version 2 is explicit. Future incompatible shapes require a version change and migration, rather than permissive fallback. Model aliases are bounded ASCII local IDs; durable UUIDs and positive SQL IDs are issued/resolved by Sylf. Models cannot provide Quest IDs, dates, rewards or execution commands inside a blueprint.

Shape validation is necessary, but does not establish ownership, source truth, cryptographic digest correctness, current database state or transaction success. Phase 1 must load owned references, calculate trusted digests, then run the pure reference/correspondence checks. No client-provided digest, lease, quality status or execution snapshot grants mutation authority. The existing server-only boundary, SQL ownership/membership guards and restricted browser grants remain required.

Canonical digest encoding is UTF-8 JSON of the parsed contract, object keys sorted recursively, absent fields omitted, and contract-defined reference sets sorted. Preserve prose after schema trimming; do not collapse meaningful instructions or rewrite academic content. Ordered activity/phase arrays remain ordered. Domain-separate hashes by artifact name and schema version. `canonicalExecutionContent` defines the semantic content projection; its result is not itself a trusted cryptographic digest. The Phase 1 hashing implementation must have golden vectors and be shared by persistence, review and apply.

## Canonical intent and versions

`CanonicalIntentV2Schema` carries title/outcome, policy and selection provenance, optional owned Subject/Goal, optional assessment identity, fixed/soft/no deadline, bounded scope with stable server scope keys/model aliases/parentage, inclusion and adopted claim references, dated learning evidence, optional research and availability, pacing/intensity/timebox preferences, assumptions and unresolved questions.

No grade, confidence questionnaire, research or deadline is mandatory for every request. Absence remains absence, rather than fabricated facts. The effective context must distinguish saved/confirmed availability from a disclosed provisional ceiling. Availability vectors use **Monday=0 through Sunday=6**; rest days and blocked civil dates are hard exclusions. Weekly/global ceilings are ceilings, never recommended educational effort. Explicit exclusions must be preserved by `validateBlueprintReferences` even when the scope appears in the allowlist.

`IntentVersionV2Schema` adds owned Plan identity, immutable version/parent, acceptance time and reason. Accepted input is immutable. Working pointer changes use CAS; active execution retains its confirmed intent until apply. A conversation append only changes `conversationVersion`.

`planningVersion` is the Plan's optimistic consequential-change counter: accepted intent changes, authoritative baseline changes and apply advance it according to the transactional protocol. A target pins the **requested** `planningVersion`. Research adoption creates one derived intent and advances this counter once; `resolvedPlanningVersion` binds alongside `resolvedIntentVersionId` in that same fenced transaction. Without adoption, resolved version equals requested version. Every later candidate/change-set comparison uses the bound resolved version. Publishing the candidate must compare the bound version and install the pointer without a further counter increment; otherwise it would invalidate itself. Apply advances the Plan version after comparing it. Unrelated conversation/XP/benign progress do not advance this counter; consequential execution changes are also checked through dependency/execution versions. This convention prevents authorized research from making its own proposal stale.

## Attempts and runtime accounting

`PlannerAttemptV2Schema` freezes owned identity, operation kind, idempotency key/request hash/time/parent, accepted text and authorization, one or two selected targets, requested/resolved intent/base/candidate/version/context correspondence, root budget, durable fence, nullable lease/checkpoint/question/error/result and write-once apply receipt.

Kinds: `PLAN`, `REPLAN`, `EXPAND`, `JOINT`, `RESEARCH_ADVICE`. States: `QUEUED`, `RUNNING`, `NEEDS_DECISION`, `SUCCEEDED`, `FAILED`, `CANCELLED`, `SUPERSEDED`. These are operation states; the Plan has only DRAFT/ACTIVE/COMPLETED/ARCHIVED. A material question requires a linked new attempt after an answer; it does not silently rebind the paused job. Terminal failed/cancelled/superseded attempts cannot resume. A successful attempt only gains its exact apply receipt. Identical retries retain key/hash; deliberate regeneration and changed intent use new keys. Key/hash mismatch is a conflict, never old-result recovery.

Benign cumulative progress does not advance the structural execution generation; start/pause/resume/end/disposition/content transitions do. Progress still carries an expected version and remains clamped/idempotent; it cannot resume a paused or withdrawn session.

Ordinary advice is a foreground response, with no Attempt/intent/revision/apply effect. Requested long research has zero mutation targets, research-only authorization, a research budget and a durable answer/evidence result. It cannot compile education or publish revisions/receipts. Explicit change requests authorize preparation; confirmation authorizes applying the exact sealed proposal.

The durable monotonic fence survives lease removal/requeue. A new acquisition/owner requires a greater fence. Lease owner/fence, expiry and database-clock checks occur in SQL for every reservation/checkpoint/publication; the pure transition helper cannot prove them. Cancellation rejects late publication. Root consumed counters cannot reset. Profile escalation retains counters/processing start; downgrade and fresh nested budgets are forbidden. Absolute deadline subtracts recorded foreground processing and never resets on takeover. See [worker runtime](WORKER_RUNTIME.md) for exact leases, supervision, budgets and recovery drills.

`ProviderCallReservationV2Schema` is an artifact in existing accounting, not another entity/queue. Its unique call/root/attempt/fence/stage/model/settlement identity precedes dispatch. It distinguishes reserved, dispatched, settled, unknown spend and proven undispatched cancellation. Actual tokens remain factual even if higher than a reservation. The root budget may retain truthful token overrun only in terminal failure/cancellation/supersession; it cannot reserve another call or publish success. Never clip actual usage to make the schema pass. Unknown pricing/spend uses null cost, never a fake zero. SQL/service uniqueness and settlement CAS must make reservation/quota settlement idempotent; external provider execution is not exactly-once.

## LearningBlueprint and research

`LearningBlueprintV2Schema` has four parts: strategy, scope dispositions, activities, decisions. Strategy has flexible pedagogical explanation/outcome, uncertain recommended effort and optional phases/readiness criteria. Scope records INCLUDED/VERIFY_FIRST/CREDITED/DEFERRED/EXCLUDED, contribution, consequential reason and evidence. Activities contain local ID, outcome/scope, type/purpose, instructions/criterion, uncertain effort and approved timebox, commitment, hard/advisory dependencies, resources/evidence, and optional stage/demand/stopping/split/window information. Decisions retain assumptions, trade-offs, uncertainty and stopping conditions.

Optional fields earn their use; the model need not fill an educational taxonomy. One activity or zero new work is valid. There is no activity-per-topic ritual, numeric topic workload floor or lexical criterion filter. Ordered estimates, valid IDs/references, dependency acyclicity, split limits and explicit hard constraints are deterministic checks. Whether a task is useful is educational reasoning/quality evaluation.

Model response has at most 60 detailed activities; a server-assembled revision may contain up to 200, including unaffected existing work. Joint model output shares the 60 bound across both Plans. Only COMMITTED work materializes. CONTINGENT work names a committed checkpoint and stays unscheduled; OPTIONAL work stays unscheduled. A committed task cannot depend on an unscheduled branch. Conceptual hard dependencies become owned execution keys; advisory order/windows cannot become hidden hard scheduling demands. Owned cross-plan dependencies are pinned in context, materialized once in the primary Plan and protected when another Plan depends on them.

`AssessmentProfileV2Schema` is a flexible record, not a curriculum registry. `ResearchEvidenceV2Schema` binds fetched/owned source identity, issuer/authority basis, retrieval/version/hash/applicability, selected pages/OCR/gaps, and anchored claims with separate excerpt/support/applicability verification. Adopted claims require all three checks. A page claim must come from an extracted page; late document pages are valid. Partial assessed-scope extraction cannot claim complete assessed scope. General model knowledge and search snippets are not verified retrieval. Source text cannot authorize changes. Actual URL safety, resource ownership, issuer verification and excerpt/claim support remain trusted retrieval/service checks.

Learning evidence separates self-report, checks, activity completion, session pace and student notes. Time/completion alone cannot prove readiness. Contradictions and uncertainty remain available to the model.

## Execution specification, lineage and remaining work

`ExecutionTaskSpecV2Schema` carries durable activity/Plan/Goal, blueprint local identity, exact educational content including **purpose**, consequential resource versions and hard dependencies, one approved total timebox, a remaining estimate with its actual-seconds basis, civil placement/timezone, and optional continuation ancestry. It has no duration aliases or caller-selected rewards.

`ExecutionStateV2Schema` is the authoritative live overlay: UNSTARTED/RUNNING/PAUSED/ENDED_INCOMPLETE/COMPLETED, OPEN/WITHDRAWN/COMPLETED remaining disposition, actual seconds, execution version, remaining forecast and re-estimation flag. Start protects work even at zero seconds and advances execution version. A session ending is not task completion; task completion is not mastery. `StudySessionExecutionV2Schema` and `StudySessionTransitionV2Schema` freeze the existing session overlay/transition wire boundary: RUNNING/PAUSED/ENDED, actual accepted focus/break seconds, timestamps/date/timezone and expected execution version. A session END has no task-completion/mastery flag. The future server transition enforces timer writer ownership and clamped/idempotent cumulative progress; a local pause snapshot or null `endedAt` does not authorize apply.

For unstarted work, remaining equals the approved timebox. For started work, an estimate of ten minutes made at actual twenty minutes becomes five after five more accepted minutes. `deriveRemainingWorkV2` returns a nonzero one-minute **sentinel** with `requiresReestimate=true` after exhausting the estimate. This is not an educational estimate or enough to claim healthy feasibility. Workspace/aggregate must expose the decision and reject healthy/confirmable presentation until resolved. Completion/withdrawal reserves zero future minutes without awarding withdrawn original completion. Actual history remains on its session dates. Capacity counts actual study plus eligible remaining commitments exactly once; past overdue work needs explicit reassignment, rather than disappearing or consuming every future day.

`QuestLineageV2Schema` evolves the existing link with immutable creation identity/baseline and current applied revision. Existing LIVE/DETACHED/DELETED/USER_RELEASED values remain explicit. DETACHED is legacy external work pending reviewed adoption, not a second V2 engine. Removed/released tombstones never resurrect; a reoffer creates a new reviewed identity. Remaining withdrawal on a started original retains its Quest/link/history, while a continuation is a separate identity. Started content/total timebox is immutable; an acknowledged paused/ended-incomplete task may change reviewed remaining placement/estimate. Running, completed and closed work reject structural mutation. Actual sessions/rewards never move or rewrite.

## Semantic diff, revision and change set

`compareExecutionSpecs` compares identity, exact normalized content/purpose/criterion/outcomes/scope/stage/resource versions/dependencies, effort and placement. Reference sets ignore ordering; prose does not. KEPT means full equality. MOVED/SHORTENED/EXPANDED/CHANGED combine. Removal/addition use distinct identities for replacements. A changed remaining-estimate basis is consequential. Rationale alone does not change the task. A false KEPT label fails `SemanticDiffEntryV2Schema`.

Stored diff entries contain compact exact-spec/content digests plus date/effort/basis, labels and reason. `validateSealedDiffCorrespondenceV2` checks them against digest-verified immutable before/after loads; exact useful instructions are retained in revisions, not copied into every diff row.

`PlannerRevisionV2Schema` seals owned intent/attempt/base, blueprint, complete detailed committed segment, forecast, context and passed quality. Compilation must preserve educational text/purpose/resources and translate dependencies. Optional/contingent work cannot silently become Quests. The strategic forecast is distinct from detailed/booked work.

`PlanChangeSetV2Schema` contains selected requested/resolved/version/base targets and proposed revision map, compact semantic diff, shared capacity/recommended-effort/compromise report, quality and one atomic receipt. One or two targets use the same apply path. It cannot modify an unselected Plan, exceed the shared new-activity bound, claim feasibility with shortfall/unresolved remaining estimates, or accept a partial/different receipt. `validateChangeSetCorrespondenceV2` checks accepted request/targets, owned revision identities, resolved context bases and published result correspondence. Apply must additionally recompute hashes, check all specs/diffs and current capacity, ownership, session protection and warning acknowledgments inside one coordinated transaction.

Context dependencies pin consequential intent, capacity, evidence/resource versions, affected Quest content/execution generations, selected Plan bases and cross-plan dependencies. Do not fingerprint XP, conversation appends or every elapsed heartbeat. Benign progress can pass deterministic revalidation; changed educational content/placement requires a new reviewed revision.

## Workspace, errors and quality

`PlannerWorkspaceV2Schema` is a derived read projection: Plan/working versions, active/candidate summaries, current/stale reasons, operation stage/recovery/question, schedule health, local dirty state, next action and allowed actions. It is not another durable state machine. Active and candidate cannot be the same artifact. Current candidate matches the working resolved intent/version. Dirty/stale/overrun proposals cannot confirm. Active history remains confirmed when a proposed deadline differs. Server reads must derive this from owned durable pointers/results, not accept it back as an apply request.

`PlannerErrorV2Schema` supplies stable code/stage, short actionable message, retry/resume status, affected refs/dates and recovery action/trace. It preserves the failure boundary and useful checkpoint. It does not expose secrets/provider text/stack traces. API/SQL mapping belongs to Phase 1 and must distinguish stale intent, protected execution, capacity, invalid/truncated output, unverified quality, timeout/provider failure, exhaustion, expired fence, cancellation and idempotency mismatch. Metrics join Plan/intent/attempt/change-set/revision/call IDs; routine logs exclude private student/source content.

Quality report binds educational/evidence digests and specific issue evidence/consequence, category/severity/resolution and verification. A repair attempt is not resolution. An unresolved severe issue cannot pass or be acknowledged away; verified repair must be tied to current content. Reasonable nonblocking uncertainty can be accepted. Warnings identify exact acknowledgment IDs. Critic subjectivity cannot automatically pad work; schema checks do not prove pedagogical excellence. Independent review/output benchmark remain later generation gates.

## One technical envelope and assembly headroom

All create/read/edit/review/apply artifacts use the same versioned 4 MiB UTF-8 outer bound. Component headroom prevents accepted artifacts failing only after wrapping: research evidence ≤1 MiB, intent ≤3 MiB, educational blueprint ≤1 MiB, derived execution copy ≤blueprint bytes +1 MiB, other revision metadata ≤1 MiB. Joint review stores compact diff/pointers and per-Plan summaries; it does not embed two full histories. Counts and bytes are both technical admission limits. Preflight/model validation must disclose required segmentation before seal; accepted components cannot be clipped, genericized or silently partially saved.

The automated envelope case exercises 500 scopes, 100 phases and 200 multilingual activities through blueprint and full revision assembly. Technical limits are not workload targets. Old records outside the envelope remain protected legacy commitments with explicit migration exceptions; no `legacy=true` escape hatch admits invalid new work.
