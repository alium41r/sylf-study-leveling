# Sylf pixel companion — Phase 1

Historical Phase 1 report: the reversible renderer and development comparison were implemented with an opaque runtime copy. The user subsequently replaced the source artwork with transparent PNGs. Phase 2 now preserves this full-art comparison using an exact copy of the supplied transparent replacement, alongside SVG and the new layered preview. See the [Phase 2 report](/Users/aliumair/Desktop/sylf/documentation/pixel-companion/phase2-report.md) for current assets and results. The observations below record the original Phase 1 run, including its then-pending transparency work.

1. **Current system.** `Companion.tsx` renders an SVG rig from `artwork.tsx`, which masks and moves parts of one WebP painting (`public/landing/companion/original-rig.webp`) and combines them with vector eyes, arms, and props. `model.ts` maps 12 semantic states to six expressions and six actions; `MagicalEyes` supplies nine eye presentations. `useCompanionState` manages a timed, priority-based reaction per instance. There is no global companion state. CSS supplies idle motion, blink, poses, and reactions; the landing journey adds scroll travel and spring-driven secondary motion. Visibility and reduced-motion handling already exist.

2. **Rendering locations.** The active hooded companion appears in the `/` landing journey, the four `/onboarding` steps, and the existing `/companion-prototype` review. An unused `StudyIslandScene` also references it. Dashboard/locker/social/profile `CharacterRenderer` avatars, the `/sylv-preview` modular SVG workbench, and the static login/register illustration are separate systems and were left untouched.

3. **Files changed for this experiment.** Added `app/components/landing/companion/PixelCompanion.tsx`, `PixelCompanion.module.css`, and `pixel-preview.ts`; `public/companions/sylf-pixel-companion.png`; `__tests__/landing/pixel-companion-prototype.test.tsx`; `scripts/verify-pixel-companion-phase1.mjs`; this report and QA evidence under `documentation/pixel-companion/phase1/`. Modified only `Companion.tsx`, `CompanionReview.tsx`, `CompanionReview.module.css`, and `JourneyCompanion.module.css` in that companion directory. The exact file list, including every screenshot and log, is in [file-manifest.json](phase1/file-manifest.json). The original artwork, SVG eye logic, state model, and animation code remain present. The CSS addition suppresses raster-only rotation/perspective during comparison. No dependencies or product preferences were added.

4. **Source art.** The full source was found at the repository root as `sylf pixel companion .png` (note the space before `.png`). It is 1254 × 1254 RGB, without an alpha channel. Source SHA-256: `fa264d93a92916a7cb553eeabb4f16f6043693414514e92600e5a63c38b69b13`. The extra `sylf pixel companion without eyes.png` was not used.

5. **Runtime art.** `public/companions/sylf-pixel-companion.png` currently preserves the original bytes. The intended transparent derivative will change only background alpha after the pending method choice. No crop, vector tracing, palette change, or body/eye redraw is planned. `PixelCompanion` loads the PNG through unoptimized Next Image with `image-rendering: pixelated` and `object-fit: contain`; no filters, glow, or image animation are applied.

6. **Where to compare.** Run `npm run dev`. Open `/companion-prototype` and use **Current SVG companion / New pixel companion**. Its links carry the selected mode into the real landing and onboarding layouts. Direct links are `/?companion=pixel`, `/onboarding?companion=pixel`, and `/companion-prototype?companion=pixel`; omit the query parameter for SVG. The switch only operates when `NODE_ENV` is `development`. The review's 15 original expression/action cards remain SVG in both modes. State/reaction controls are disabled during the static pixel preview. Nothing is persisted to an account or browser preference.

7. **Sizes and device coverage.** Browser SVG baseline: 1440 × 1000 desktop, 1024 × 900 and 820 × 1180 tablet, 390 × 844 phone, and 320 × 740 narrow phone at device-pixel ratios 1, 2, and 3. Landing boxes are respectively 144 × 180, 120 × 150, 96 × 120, and 56 × 70 CSS pixels. The square pixel canvas fits at widths 144, 120, 96, and 56 without distortion. Onboarding uses 110, 130, and 140 px slots; the real Welcome slot is verified at 130 px. Existing review uses 320 px desktop and 260 px mobile, with 180 px SVG gallery cards. The pixel QA script also samples 192 and 288 px in the existing review as temporary diagnostic overrides.

8. **Pixel/Retina limitations.** The supplied raster contains apparent cells around 12–14 source pixels wide rather than a uniform native grid, so 192/288 px are approximate friendly scales, not certified integer scales. Source padding reduces the visible silhouette at the smallest landing slot to approximately 36 × 47 CSS px and each eye to about 5 px. Retina provides more device pixels but cannot restore detail lost through small layout sizing or repair source edge artifacts. The raster bypasses SVG tilt and perspective; the existing journey's fractional translation still needs assessment during pixel movement. Transparent-copy visual QA remains pending.

9. **Layout fit and visual verdict.** The prototype shares the existing boxes and requires no architectural changes. The SVG baseline passes 43 browser checks, including protected onboarding with a temporary synthetic identity and intercepted stats in an isolated browser; no account submissions or writes occur. A reliable better/worse verdict awaits the transparent-copy comparison. Small-size eye readability is the main concern. The complete pixel artwork should be judged on the existing light review canvas, dark onboarding card, and landing scene after removing the unintended black rectangle.

10. **Eye sheets.** `eye batch 1.png` through `eye batch 7.png` were all found at the repository root. None were implemented, modified, cropped, converted, relocated, or integrated.

11. **Future architectural compatibility.** The current semantic state API can later drive a base pixel body and registered isolated eye overlays cleanly. The raster presentation needs its own pixel coordinates and discrete animation handling rather than reuse of the SVG masks and deformation. No new global state layer is needed merely to render expressions. The separate product avatar systems should receive their own migration decision.

12. **Recommended Phase 2.** First settle the art direction and smallest usable size. Then validate the eyeless body plus a few isolated eyes on one shared native grid, implement neutral/happy/thinking states and a small blink animation, and check alignment at integer-friendly sizes on the same surfaces. Defer equipment, accessories, customization, a full animation engine, and wider migration until that small expression study succeeds.
