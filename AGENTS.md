## Working model

- Sylf is a study/progression app: Next.js 16 App Router, React 19, strict TypeScript, Tailwind CSS 4/CSS Modules, and Prisma/PostgreSQL. Use npm and `package-lock.json`; `@/` resolves to the repository root.
- Routes, UI, and API handlers live in `app/`; shared engines, contracts, services, and catalogs in `lib/`. Before architectural decisions, inspect relevant implementations, consumers, and tests. Extend existing owners rather than creating parallel state, persistence, calculations, or UI systems.
- Web composition starts at `app/layout.tsx`, `app/components/GlobalSystemWrapper.tsx`, and `app/components/SylfAppShell.tsx`. `mobile/` is a Vite/Capacitor client reusing screens/providers through navigation/API adapters. Preserve shared boundaries; keep database/server-only code and provider credentials out of client imports.
- Scope changes to the request, follow nearby conventions, and preserve unrelated working-tree changes. Avoid unrelated refactors and cleanup.

## Existing authorities

Inspect these owners and their callers before changing behavior:

| Area | Owners and invariants |
| --- | --- |
| Study timer | `lib/timer-engine.ts`, `lib/timer-leader.ts`, and `app/focus/components/FocusScreen.tsx`: derive time from epoch snapshots; preserve single-writer tab leadership and separate focus/break accounting. |
| Progression and rewards | `lib/game-engine.ts`, `lib/difficulty-engine.ts`, `lib/session-math.ts`, `lib/cognitive-stats.ts`, and `lib/skill-tree.ts`. Settlement/reward claims also use atomic PostgreSQL RPCs; preserve transactions, ledgers, and replay guarantees. |
| Schedule and subjects | `lib/study-schedule-service.ts` resolves fixed/floating rest days; `lib/timezone-service.ts` handles user-local dates; `lib/subject-service.ts` defines active-subject filtering/lifecycle dependencies. Reuse these across manual, AI, and calendar flows. |
| Planner and AI | `lib/planner/contracts.ts` and `lib/planner/server/` own revisions/materialization; `lib/planner/server/mutation-guards.ts` protects linked quest/goal edits. Reuse `lib/ai/` routing, provider adapters, model configuration, entitlements, and quota accounting. See the [Planner index](documentation/planner/README.md). |
| Authentication and data | Protected APIs use `getSession` from `lib/auth-server.ts` for cookie authentication/revocation plus resource ownership checks; `proxy.ts` redirects are insufficient authorization. Use `lib/prisma.ts`; inspect `prisma/schema.prisma` and ordered `prisma/migrations/`, including RPCs, triggers, and RLS. |
| Shared client systems | Reuse `AuthProvider`/`refreshStats`, `lib/api-transport.ts`, and `lib/client-data-cache.ts`; preserve mutation invalidation and logout cleanup. Audio uses Acoustics/CustomAudio contexts and `lib/acoustics/`; Focus Parties use `lib/focus-party-service.ts` and their shared context. |

Preserve polling fallbacks for Supabase Realtime and in-process fallbacks for Redis. Reuse shared `lib/` catalogs rather than copying content definitions into pages. Schema changes need corresponding migrations and `npx prisma generate`; update `SCHEMA_BUILD_VERSION` in `lib/prisma.ts` when fields change.

## Appearance

- Appearance supports light/dark modes, custom accent/background colors, and legacy presets. Use semantic tokens in `app/globals.css`, generated by `lib/color-utils.ts` and applied by `GlobalSystemWrapper`. Never assume a fixed palette or dark surfaces; `ThemeProvider` alone does not implement appearance.
- Follow `app/settings/appearance/` for persistence/application. Preserve preference synchronization and contrast handling; use foreground/accent contrast tokens appropriate to the actual surface.
- Focus backgrounds have a separate catalog/preference flow: `app/focus/hooks/useFocusBackground.ts` and `lib/focus-background-preference.ts`. Extend it instead of adding another selector/store.

## Documentation

- Start at the [documentation index](documentation/README.md) and relevant feature index/current contract. Source, tests, schema, and configuration resolve discrepancies. Reports/audits and QA evidence describe their own run; phase specs are design inputs, not proof of current behavior. `FINAL`/`ARCHITECTURE` filenames do not establish current requirements.
- Consult the [design index](documentation/design/README.md) before using the `documentation/design/design-system/` reference set: its generic master and older landing guidance have explicit limitations. `archive/` holds dormant material; `antigravity project template/` is a starter, not Sylf's architecture specification.
- Update current docs when behavior changes. Put new reports in `documentation/<feature>/reports/<task-or-phase>/`, with evidence beside them; preserve established evidence/writer paths described by the indexes. Link detailed contracts instead of copying them here.
- Load only documentation relevant to the current task. Do not exhaustively read historical reports, evidence, or unrelated feature documentation unless the task requires it.

## Commands and verification

Check `package.json` and tool configuration when commands change.

| Purpose | Command |
| --- | --- |
| Web development | `npm run dev` |
| Production build / serve | `npm run build` / `npm run start` |
| Tests | `npm run test -- --run [path-filter]` (Vitest; `npm test` watches) |
| Typecheck | `npx tsc --noEmit`; run `npx next typegen` first on a fresh checkout or after route changes |
| Lint | `npx eslint <changed-files>`; `npx eslint .` for a full audit |
| Mobile build / bundle checks | `npm run mobile:build` and `npm run mobile:verify` |
| Planner database integration | `node scripts/test/test-planner-postgres.mjs [path-filter]` (disposable PostgreSQL; Docker required) |

`npm run lint` currently invokes the removed `next lint`; use ESLint directly. Next.js builds do not run linting.

For meaningful code changes, run relevant tests, typecheck, and lint; add regression coverage for changed behavior. Build for routing, shared-screen, server/client boundary, configuration, or dependency changes; run mobile checks for shared client changes. Visually verify UI at relevant desktop/mobile sizes, in both modes and with custom colors. Database/provider suites may be opt-in: inspect prerequisites, report skipped coverage/blockers, and distinguish existing failures from regressions. Documentation-only edits need content, reference, and diff checks.
