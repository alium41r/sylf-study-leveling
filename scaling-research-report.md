## 1. Video 1 — "How I Scaled My NextJS + Supabase App To Handle 10,000 Users"

Source: [official YouTube description](https://www.youtube.com/watch?v=B-8kYeNB_6M) (the video's own summary enumerates the optimizations). This video covers the **0 → 10,000 users** phase, which the creator later calls "the hardest part… that's when the biggest inefficiencies came out" ([45k transcript](https://www.texttube.ai/read/CiavEwBMGSY/scaling-yorby-to-45000-users-with-superbase-optimizations)).

Concrete optimizations mentioned:

- **Upgrade the Supabase instance (vertical scale / compute add-on).** The description explicitly lists "upgrading my Supabase instance" as the first step — bumping the compute tier to get more CPU/RAM for the database ([10k description](https://www.youtube.com/watch?v=B-8kYeNB_6M)).
- **Diagnose slow queries before optimizing anything.** The description lists "diagnosing slow queries" as a discrete step — i.e. profile with `pg_stat_statements` to find the top offenders rather than guessing (same pattern the playbook spells out in SQL: `SELECT query, calls, total_exec_time … FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20` — [playbook](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook)).
- **Add missing database indexes.** "Adding missing database indexes" is called out explicitly; Postgres adds no indexes automatically, and unindexed filter/sort columns degrade to `Seq Scan` once tables grow ([10k description](https://www.youtube.com/watch?v=B-8kYeNB_6M), [lessons-learned](https://www.iloveblogs.blog/post/nextjs-supabase-lessons-learned-production)).
- **Improve caching with Redis.** The description names "improving caching with Redis" — introducing a dedicated cache layer (Redis/Upstash-style KV) in front of expensive/repeated reads rather than hitting Postgres every time ([10k description](https://www.youtube.com/watch?v=B-8kYeNB_6M)).
- **Use AI to analyze performance bottlenecks.** "Leveraging AI to analyze performance bottlenecks" — feeding slow-query/error telemetry into an LLM to triage and propose fixes. (This is the same workflow he later formalizes in the 45k video as an "AI SRE" fed PostHog errors into a local LLM — [45k transcript](https://www.texttube.ai/read/CiavEwBMGSY/scaling-yorby-to-45000-users-with-superbase-optimizations).)

## 2. Video 2 — "How I Scaled My NextJS + Supabase App to 25,000 Users"

Source: [official YouTube description](https://www.youtube.com/watch?v=k-ETON-f7Sw) + [chapter index](https://www.youtube.com/watch?v=k-ETON-f7Sw) (`Stack and Infrastructure Choices`, `Moving Beyond Fully Serverless`, `Fixing Our Supabase Connection Bottleneck`). This covers the **10k → 25k** phase.

Concrete technical optimizations mentioned:

- **Move part of the stack off fully-serverless infrastructure.** The description explicitly says the technical issues included "moving part of the stack away from fully serverless infrastructure" — i.e. stop running *everything* in short-lived serverless functions once DB-bound workloads outgrow them ([25k description](https://www.youtube.com/watch?v=k-ETON-f7Sw)).
- **Fix Postgres connection pooling issues.** "Dealing with Postgres connection pooling issues" — the classic serverless problem where every function invocation opens a fresh Postgres connection and exhausts the pool (the chapter is literally titled "Fixing Our Supabase Connection Bottleneck") ([25k description](https://www.youtube.com/watch?v=k-ETON-f7Sw); see also [Supabase CONNECT_TIMEOUT / hanging-query troubleshooting](https://supabase.com/docs/guides/troubleshooting/troubleshooting-connect_timeout-or-hanging-queries-in-vercel-serverless-functions-775f92)).
- **Add a dedicated server to handle more database operations.** The description names "adding a dedicated server to handle more database operations" — running persistent, always-on processes for DB-heavy work instead of relying on serverless invocations ([25k description](https://www.youtube.com/watch?v=k-ETON-f7Sw)).
- **Use Upstash Workflows for background/async work.** "Using Upstash workflows" — offloading long-running/queued jobs out of the request path ([25k description](https://www.youtube.com/watch?v=k-ETON-f7Sw)). This matches the playbook's "offload sends to a queue / job queue" pattern so user-facing endpoints only enqueue ([playbook](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook)).
- *(Business/retention — not a DB optimization, for completeness:)* reducing churn by shifting ICP from prosumer creators to brands/agencies with lower churn ([25k description](https://www.youtube.com/watch?v=k-ETON-f7Sw)).

## 3. Video 3 — "How I Scaled My NextJS + Supabase App to 45,000 Users"

Source: [full transcript via TextTube](https://www.texttube.ai/read/CiavEwBMGSY/scaling-yorby-to-45000-users-with-superbase-optimizations) (also mirrored at [React Libraries](https://reactlibraries.com/videos/how-i-scaled-my-nextjs-supabase-app-to-45-000-users-3gmfbm)). This video is explicitly "the two specific changes that made the biggest difference" — the creator states no big infra overhaul was needed at 45k; the wins were database/auth layer fixes.

Concrete optimizations mentioned:

- **Reduce / eliminate Row-Level Security (RLS) checks on server-side queries.** His RLS "team validity" check was "always a little slow and it would rack up… latency would build up over many many queries over and over again." The fix: "we actually ended up moving off of using row level security rules and just querying the database without any row level security rules in place and that significantly improved the performance" ([45k transcript](https://www.texttube.ai/read/CiavEwBMGSY/scaling-yorby-to-45000-users-with-superbase-optimizations)).
- **Keep RLS only where it matters (browser/anon clients), not the server path.** He explains RLS is "crucial for browser instances where public and user-scoped keys are exposed," but "if you're… doing all your data fetching server side via a Supabase server client or even a Supabase admin client then… row level security rules become a lot less important" — enforce authorization in the API/server layer instead ([45k transcript](https://www.texttube.ai/read/CiavEwBMGSY/scaling-yorby-to-45000-users-with-superbase-optimizations)).
- **Migrate `getUser()` → `getClaims()`.** `getUser()` "required a server-side round trip, potentially taking 1–2 seconds." `getClaims()` "just uses a JWT token locally… you can still get the currently authenticated user… but you do not need to do that round trip to the Supabase API server." This removes the auth round trip from the hot path ([45k transcript](https://www.texttube.ai/read/CiavEwBMGSY/scaling-yorby-to-45000-users-with-superbase-optimizations)).
- **Plan to consolidate all server-side querying on the Supabase admin client.** He notes "considering migrating all data querying to the Supabase admin client for consistency with other database providers" — i.e. server code uses the `service_role`/admin client and bypasses RLS, treating Supabase like a plain Postgres ([45k transcript](https://www.texttube.ai/read/CiavEwBMGSY/scaling-yorby-to-45000-users-with-superbase-optimizations)).
- **Vertical scale as a stopgap.** "The app runs on the same Supabase tier, with increased compute size costing around $200/month" ([45k transcript](https://www.texttube.ai/read/CiavEwBMGSY/scaling-yorby-to-45000-users-with-superbase-optimizations)).

## 4. Consolidated Playbook — Top ~12 for Your Specific Symptoms

**Your stack/symptoms:** Next.js App Router · Prisma over Supabase Postgres via the **transaction pooler** (Supavisor/pgBouncer) · client components polling **REST API routes every ~12s**. Symptoms: (a) slow client-side routing, (b) slow friend-list/message fetches, (c) slow stats fetches, (d) slow online/offline presence updates, (e) slow profile fetches.

Symptom key: **(a)** routing · **(b)** friends/messages · **(c)** stats · **(d)** presence · **(e)** profiles.

1. **Stop polling Postgres through the DB on every 12s tick — add `Cache-Control: s-maxage=<n>, stale-while-revalidate=<n>` to every REST route** and give each endpoint a revalidation window. With many clients polling identical public/aggregate endpoints every 12s, a CDN/edge cache absorbs the repeated hits; the DB only sees one refresh per window. This is the single highest-leverage fix for a 12s poll loop ([playbook, "Add a real edge cache for API responses"](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook)). Use short `s-maxage` (~10–15s) only where freshness actually matters, longer for stats.
2. **Add a client-side stale-while-revalidate cache (TanStack Query `staleTime` + `refetchInterval`, or SWR) so the 12s poll becomes a background refresh.** Pages render instantly from the cached snapshot and swap in fresh data when it arrives, instead of blocking navigation on a fetch. This directly fixes **(a)** and **(e)** and dedupes concurrent poll requests across open tabs/components ([Next.js Router Cache / SWR pattern](https://www.iloveblogs.blog/post/nextjs-supabase-lessons-learned-production)).
3. **Give every route a `loading.tsx` + `<Suspense>` boundary, and `router.prefetch()`/`<Link prefetch>` the destinations.** Client-side routing feels slow because navigation is blocked on `useEffect` fetches after mount. Streaming a static shell + skeleton immediately and prefetching link targets in the background makes **(a)** feel near-instant without any DB change ([lessons-learned, "Server Components Are Your Friend"](https://www.iloveblogs.blog/post/nextjs-supabase-lessons-learned-production)).
4. **Fix the Prisma + transaction-pooler setup** for **(a/b/c/e)** reliability and latency: connect with the Supavisor/pgBouncer **transaction-mode** URL and append `?pgbouncer=true` (makes Prisma skip server-prepared statements, which transaction-mode pooling cannot support across transactions); keep the **session/direct** connection string *only* for `prisma migrate`/CLI; size `connection_limit` per serverless instance so bursty polls don't exhaust the pool; and wrap DB calls in a retry for `ECONNRESET`/`57P01`/`Connection terminated`. Pool exhaustion is the exact "connection bottleneck" the [25k video](https://www.youtube.com/watch?v=k-ETON-f7Sw) hit ([lessons-learned §6](https://www.iloveblogs.blog/post/nextjs-supabase-lessons-learned-production), [pooling guide](https://www.iloveblogs.blog/guides/supabase-connection-pooling-vercel)).
5. **Consolidate friend-list + message fetches into one query with `Promise.all` on the server — or better, one SQL query.** Replace the N client-side round trips (friend list, then per-friend profile, then last message) with a single REST endpoint that issues independent queries in parallel (`Promise.all`) and/or a single Postgres join/aggregate (`SELECT … FROM friendships f JOIN profiles p ON … LEFT JOIN LATERAL (SELECT … FROM messages ORDER BY created_at DESC LIMIT 1)`). Kills the N+1 that makes **(b)** slow ([lessons-learned §3 "N+1"](https://www.iloveblogs.blog/post/nextjs-supabase-lessons-learned-production), [playbook "Index the N+1 queries"](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook)).
6. **Add composite/partial indexes for the exact filters, and index RLS predicates** for **(b/c/e)**: `friendships(user_id, friend_id)`, `messages(conversation_id, created_at DESC)`, `profiles` lookups, and any column used in a `WHERE`/`ORDER BY`/RLS `USING`. Use a **partial index** (`… WHERE status = 'accepted'` or `… WHERE deleted_at IS NULL`) to keep it small when only a subset of rows matches. Verify with `EXPLAIN ANALYZE` that you switch `Seq Scan → Index Scan` ([lessons-learned §2](https://www.iloveblogs.blog/post/nextjs-supabase-lessons-learned-production), [10k video](https://www.youtube.com/watch?v=B-8kYeNB_6M)).
7. **Rewrite the stats endpoint as aggregate SQL, not per-entity counts.** One `SELECT date_trunc('day', created_at), count(*) … GROUP BY 1` (or a `materialized view` / denormalized counter updated by an `AFTER INSERT/DELETE` trigger) replaces the N+1 "count posts, then count likes, then count followers…" that makes **(c)** slow. Precompute counters in the DB (trigger) rather than in application code to avoid one extra round trip per write ([playbook §Stage 4 "triggers instead of application-level denormalization"](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook)).
8. **Cache stats and profiles with `unstable_cache` (or `revalidate` on the route) + tag invalidation.** Stats don't need 12s freshness — cache them `revalidate: 60–300s` and call `revalidateTag('stats')`/`revalidatePath()` only when a real write occurs. This removes the poll loop from the DB entirely for **(c)** and **(e)** ([playbook "Cache the expensive reads"](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook), [lessons-learned §5](https://www.iloveblogs.blog/post/nextjs-supabase-lessons-learned-production)).
9. **Throttle presence heartbeats — do NOT `UPDATE` a `last_seen` row on every 12s poll.** That's textbook write amplification: N users × ~7k updates/hour each = a wall of writes the playbook flags ("An `UPDATE` on every page view (recording 'last seen' per session)"). Write `last_seen` at most every 30–60s, and batch/absorb the rest ([playbook §Stage 4 "Audit your write amplification"](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook)).
10. **Move presence out of Postgres entirely — use Supabase Realtime's presence channel (in-memory, ephemeral) or a Redis (Upstash) `SET key EX 60` with TTL.** Presence is ephemeral state, not durable data: track "online now" in memory/Redis with a short TTL so the poll only checks a cheap key, and persist `last_seen_at` to Postgres on a slow cadence or on disconnect. This both fixes **(d)** and stops presence from starving the pool (the "move realtime off the primary / filter subscriptions" principle) ([playbook §Stage 4](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook)).
11. **Cut the poll loop where it exists by switching to push: Supabase Realtime `postgres_changes` (or a WebSocket) for friends/messages/presence**, so clients refetch only when a row actually changes instead of hammering REST every 12s. If you must keep polling, raise the interval for slow-moving data (stats/profiles) and add request coalescing so N tabs don't issue N polls ([playbook "Move realtime off the primary"](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook)).
12. **Optimize or bypass RLS server-side — the 45k video's core win.** If your server fetches go through RLS (especially team/org `USING` checks), either: (i) wrap `auth.uid()` in a subquery — `using ((select auth.uid()) = user_id)` — so it's evaluated once and cached instead of per-row, use a `SECURITY DEFINER` helper (`private.is_team_member(team_id)`) for membership checks, and index the policy columns; or (ii) do what Yorby did and serve reads through the **`service_role`/admin client** (or a Postgres role that bypasses RLS), enforcing authorization in your API layer, keeping RLS only for browser/anon clients. RLS predicates on unindexed columns + per-row function calls are exactly the "rack up latency over many queries" problem he describes ([45k transcript](https://www.texttube.ai/read/CiavEwBMGSY/scaling-yorby-to-45000-users-with-superbase-optimizations), [Supabase agent-skills RLS reference](https://github.com/supabase/agent-skills/blob/main/skills/supabase-postgres-best-practices/references/security-rls-performance.md), [RLS docs](https://supabase.com/docs/guides/troubleshooting/rls-performance-and-best-practices)).

**Two cross-cutting notes on your setup:**

- **Auth round trips.** If any of these REST routes call Supabase `auth.getUser()` to resolve the caller, switch the hot path to `getClaims()`/`getSession()` (local JWT decode — zero network) and reserve `getUser()` for security-critical operations only. This is the 45k video's second fix and removes up to 1–2s per request ([45k transcript](https://www.texttube.ai/read/CiavEwBMGSY/scaling-yorby-to-45000-users-with-superbase-optimizations), [playbook "Move session lookups out of the hot path"](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook)).
- **Background/offload work.** Anything the poll triggers that isn't user-facing (analytics, notifications, presence aggregation, feed precompute) should be enqueued — Upstash Workflows/QStash (the [25k video](https://www.youtube.com/watch?v=k-ETON-f7Sw)'s choice) or a jobs table + cron — so the REST handler only enqueues and returns ([playbook §Stage 3](https://www.iloveblogs.blog/guides/scaling-nextjs-supabase-0-to-100k-users-playbook)).
