# Step 1 supporting artifacts

The new schemas live under `lib/planner/v2/intelligence/schemas/`; the Phase 0 contract files and barrel remain byte-identical. These artifacts support the approved compiler inside existing Plan/Attempt/Revision ownership. They introduce no persistence, API endpoint, worker handler or execution writer.

| Artifact | Boundary |
| --- | --- |
| Assistant response | Answer, question, suggested change or proposed action; bounded local plan aliases. No durable IDs, Quest IDs, authorization or mutation commands. A `PROPOSAL` is model output requiring separate server authorization, never authorization itself. |
| Scheduling envelope | User-local civil dates, bounded detailed window, capacity digest, daily shape, weekly/per-goal ceilings, deadline, disclosed availability basis, reserve deductions and protected actual/remaining execution. Its finite detailed window does not turn an open goal into a deadline. The daily accounting identity prevents inconsistent subtraction; the future producer must obtain authoritative facts and apply reserve once. |
| Allocation report | Every placed/unplaced committed activity with its exact timebox; feasibility or a proved capacity shortfall or unresolved allocation; consequential density/window/switching/finish/estimate/order findings with evidence and consequence. A capacity proof requires required minutes above the usable capacity bound. The future deterministic allocator must establish the validity of that bound; schema validation cannot prove scheduling feasibility. |
| Research processing | Query/fetch/follow-up and selected extraction receipts; source hashes/pages/OCR/character counts bound across sources; optional frozen evidence bundle. Excerpts, support/applicability and partial/completeness claims reuse frozen research validation. Schema shape does not prove ownership, issuer authenticity or excerpt truth; the research service must do that. |
| Compiler checkpoint | Versioned stage data bound to owner, exact request/root/authorization, requested/resolved intent identities and digests, target bases/candidate/version/context dependencies, source pins and scheduling envelope. Later stages add hashed blueprints/allocation and per-target frozen quality reports attesting to the exact content/evidence and reviewed schedule. Adaptation and repair are bounded to one; repairs name known issues. |

`intelligence/checkpoints.ts` is a Node boundary using the existing Phase 1 hash owner. It checks the existing Attempt checkpoint header/digest/stage, exact attempt fields and target correspondence, then compares a **fresh trusted binding** and all artifact digests. Callers must construct expected bindings from owned immutable intents, durable source receipts and current execution context. Copying the stored binding into `expected` in production would defeat freshness; tests do so only for an unchanged fixture, and independently alter expected facts to test rejection. Lease/fence/cancellation/persistence authority stays in existing Phase 1 services.

Checkpoint schemas describe the last completed stage, not a second lifecycle state machine. Research checkpoints may precede resolution or have zero targets for research advice. Educational stages require resolved context for selected targets. Quality issue IDs are unique across targets and share the existing 60-issue bound. A repair cannot pass before verification, and even a repaired warning needs a verified named resolution. Quality-stage data can retain a blocked/incomplete report for recovery; it never becomes a confirmable revision without Phase 1's independent publication and apply checks.

Checkpoint snapshots reference persisted intents by identity/digest instead of embedding and duplicating up to two large canonical intents. Research receipts can retain `evidence: null` after the verified bundle has been adopted into an immutable resolved intent or persisted by its existing owner; this is pointer-based reuse, not discarding raw evidence. The producing/recovery services must reload and validate those owned artifacts. Source pins still identify exact selected content.

Stored blueprint snapshots allow up to 200 outstanding activities per target to carry retained education. Model generation still uses the frozen 60-new-activity bound shared across two targets. Every committed snapshot activity must appear exactly once in an allocation report; optional/contingent work cannot be booked. Shared hard prerequisites are checked for cycles. Full execution reference resolution, hard windows, per-day/week feasibility, source ownership and existing activity membership remain deterministic compiler/Phase 1 responsibilities.

Every artifact uses existing nested count/string/byte limits and the common 4 MiB ceiling. Each individually valid nested artifact does **not** guarantee their combination fits. Oversized combinations fail explicitly without mutation/trimming. The maximum-count witness covers two plans, 200 stored activities/500 scope nodes/100 phases each, 200 research claims, 60 added plus 340 retained execution entries, durable Attempt transport, revision read and apply receipt shapes. This is serialization/correspondence evidence; actual database publish/read/apply remains a required Step 5/6 integration gate.
