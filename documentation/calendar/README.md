# Calendar

Sylf's calendar combines personal events, connected calendars and daily notes with the existing study schedule. The shared web/mobile entry point remains `app/components/Calendar/StudyCalendar.tsx`; it composes `app/calendar/components/CalendarWorkspace.tsx`.

## Current contract

- **Month** offers a date overview, event/quest/deadline chips, note previews, and optional study intensity. **Week** offers a seven-day agenda that becomes a readable vertical list when the actual content area is narrow. **Day** offers the daily workspace directly. Optional time planning adds a scrollable time grid to both views, with a compact date-based agenda below it. Changing views shares the same month projection, without an empty refetch between views.
- Selecting a date reveals events, quests, goal deadlines, multiple notes, and study details. On narrow layouts, pointer selection brings the workspace into focus. Today, previous/next, a date picker, and month arrow-key navigation use civil dates rather than device-local midnight.
- `StudyScheduleService` remains the authority for study history, quests, goal deadlines, daily targets, fixed/floating rest days, and Planner behavior. Its existing month API and study-schedule mutation APIs are reused. Personal events do **not** change study targets, earn rewards, or reserve Planner capacity.
- Personal content lives in `CalendarEvent` and `CalendarNote`, related to the canonical integer `User.id`. UUIDs identify content independently of the date it is attached to. Content never enters `characterConfig`, quests, goals, or preferences. Only pending writing drafts use owner-scoped device recovery storage; they are cleared after acknowledgement and on logout.
- All-day events store civil dates as `[startDate, endDate)`, with no UTC instants. The editor displays an inclusive final date. Timed events store `[startsAt, endsAt)` as UTC timestamptz values plus an IANA timezone and matching date keys in that timezone. Rendering uses the account timezone; editing preserves the event's original timezone. Midnight ends do not create a phantom entry on the next date.
- Date notes store `dateKey` and a versioned document. Existing `{ version: 1, text }` notes remain readable and unchanged until edited. Version 2 adds `mode: "note" | "annotation"` and `ink: { width: 1000, height: 1400, strokes }`. Typed text and editable pen/highlighter strokes coexist in one note. Optional titles, multiple notes per day, and date changes remain supported. Ink uses point tuples `[x, y, pressure]`, semantic colors, bounded geometry, and subpixel simplification at stroke boundaries. A page is never flattened into an image.
- The daily notebook autosaves after a writing pause and serializes writes. Changes made during a request are retained for the next revision. Pending drafts are stored under `sylf_calendar_draft:<owner>:...` with a writer-specific identity. Recoveries are offered on the calendar and resume saving when reopened. Connectivity retries back off; acknowledged-late writes are reconciled with an owner-scoped `GET /api/calendar/personal?id=...` before retrying. Conflicts retain the local draft and offer a separate copy. Quota/storage failures are explicit and prevent a silent close; pending in-memory jobs and unload protection provide additional recovery while the page stays open. Logout clears drafts and invalidates pending writers through the shared client-session epoch.
- Calendar annotations reuse `CalendarNote` and the same service, with `mode: "annotation"`; they are omitted from ordinary journal lists. A stroke references its owning date and a semantic `day`, `date`, `event:<id>`, `quest:<id>`, or `goal:<id>` anchor. Geometry is local to that anchor, with a reference size, and scales uniformly when layout changes. Optional semantic endpoints route cross-date connectors when both ends are present. If an endpoint is outside the current view, the primary portion is retained and clipped to the current calendar; annotations on a removed/hidden item remain stored and reappear when that anchor is available. No document stores viewport origins or changes the study schedule. Hide/show and explicit annotation mode preserve normal calendar interaction.
- Input uses Pointer Events, optional coalesced samples, pointer capture, smoothed pressure ribbons, and an imperative active SVG path. React updates at stroke boundaries, with memoized saved paths. Pen/mouse write; fingers pan by default, while an explicit finger-drawing toggle enables touch ink. Two-finger panning/pinch zoom, pan tool, stroke eraser/hardware eraser input, colors, thickness, undo/redo, zoom, and expanded writing are supported. Palm-sized touches and recent pen-contact touches are rejected. Outside writing/annotation mode, the read-only overlay has no pointer events.
- New events and notes use a stable client-generated UUID across create retries. Identical retries replay the saved record; different content under an already saved identity returns a conflict. Every update and delete includes the last seen revision in its atomic owner-scoped predicate. Conflicts never silently overwrite another tab's edit.
- `GET/POST/PATCH/DELETE /api/calendar/personal` uses `getSession` with revocation checks. Caller-supplied ownership is rejected. Reads are limited to 93 days, use `private, no-store`, and return private owner-scoped notes/personal events plus events in owned or accepted shared calendars. Writes validate content, timezones, date consistency, payload size, and chronological order. RLS is enabled with no public policies and direct `anon`/`authenticated` table privileges are revoked. Access goes through Sylf's backend role and ownership checks, not Supabase `auth.uid()`.
- Editors use a native modal dialog, explicit keyboard wrapping, focus restoration, Escape handling, background inertness, and reduced-motion styling. Appearance uses Sylf's actual surface/text/accent tokens, including surface polarity independent of mode. Responsive decisions use a named container, since the shared sidebar can substantially reduce usable width on tablets.

## Scheduling and progressive disclosure (Phase 3)

- The default interface stays simple: date navigation, month/week/day, quick add, personal events, study objectives, daily notebooks, and one settings entry. Writing tools and study statistics remain available through small disclosures. **Calendar settings → Advanced Options** independently enables time planning, workload insights, calendar organization, and expanded event details. A basic reminder remains in the simple event form. Repeat rules, additional reminders, colors, categories and descriptions are always available through **More options**, without a global advanced-mode prerequisite.
- `CalendarPreference` stores account display settings and a revision, through authenticated `GET/PATCH /api/calendar/preferences`. It is created only on the first explicit preference change. Writes serialize in the client, merge explicit patches after revision conflicts, and surface unsynced failures with retry. Presentation changes never mutate event/note content or cancel reminders. Turning organization controls off restores the complete content display while retaining the saved filters. Annotation visibility remains a remembered display choice. Browser alert permission is necessarily a separate device/browser choice.
- Personal events add `category`, bounded reminder offsets, a typed recurrence JSON rule, and an indexed `recurrenceThrough` bound. Daily, weekly selected weekdays, monthly date or ordinal/last weekday, yearly, intervals, inclusive end dates, and bounded occurrence counts are supported. Short months and non-leap years skip invalid dates rather than drifting. Recurrence follows the event's IANA wall time; nonexistent clock-change times are omitted and repeated minutes choose the earlier instant. The seed retains its exact original instant. **Counts count scheduled civil dates**, including a skipped DST slot; this policy is stated in the form. Recurring spans are bounded to one year and the supported date domain is 2000–2100.
- `CalendarEventException` stores only explicit overrides/cancellations, keyed by series ID and original civil date. Ranged reads expand series into virtual occurrences; they never materialize future copies. A moved occurrence keeps `occurrenceDate`, even after moving outside its original month. Series revision serializes occurrence writes with whole-series edits. Editing the whole series loads its seed through an owner-scoped event-by-ID read; duplication creates a new independent event. Existing occurrence edits are retained when rules change and apply only to original dates still in the current rule. Restoring a matching date restores its retained edit. Deleting a series cascades its exceptions and receipt records.
- Time blocks are a category of `CalendarEvent`, using the same service and revisions. They do not create study sessions, duplicate quests, reserve Planner capacity, award progress, or change a plan. Actual study-session history comes from `StudyScheduleService`; Planner-linked quests are labeled planned study and remain date-based. Structural edits to those objectives continue through Objectives/Planner and their existing guards.
- Time grids expose half-hour creation, 15-minute snapped move/resize handles, pointer capture on a stable grid root, preview feedback, edge scrolling, cancellation, and keyboard alternatives. Month move handles support date changes when time planning is enabled. Touch scrolling remains available away from explicit handles. A drop mutates only the chosen personal occurrence. Viewer-zone drops convert back into the original event timezone; nonexistent wall minutes fail visibly. An entire series can be rescheduled in the event editor. Overlapping events use separate lanes; conflict flags compare actual instants, including repeated DST hours. A civil clock grid retains a folded-hour commitment with an elapsed-duration span when its end clock precedes its start, and the time label includes both offsets.
- Workload summarizes the union of timed commitments within the explicitly labeled **08:00–20:00** window, plus conflicts and the largest open interval. It includes hidden events so filters cannot make a booked interval appear free. All-day commitments are counted separately. These summaries describe personal commitments, not Planner study capacity or a promise that the user is available. Per-day clock boundaries are memoized as pure timezone calculations; historical skipped civil dates fall back to civil-grid presentation.
- Event operations persist their exact method/body/revision/mutation UUID under `sylf_calendar_event:<owner>:...` before sending. Retry uses the exact command. The server stores a last-mutation identity/hash, and atomic ownership/revision checks reject changed retries or conflicting edits. Acknowledged-late retries replay while the mutation is still current; a later edit returns a conflict. Failed operations remain reviewable after reload, with copy recovery for writes. If device storage is unavailable, an owner-scoped in-memory registry and unload protection retain the operation in the open tab, with explicit UI wording. Logout clears pending event/note data and invalidates old writers through the shared client-session epoch.
- `CalendarReminderAgent` runs once in the shared web/mobile system wrapper. Authenticated `POST /api/calendar/reminders` reads reminder-bearing events only, expands a bounded nearby range, and checks the existing notification preferences. It locks the series and atomically inserts `CalendarReminderReceipt` claims with the existing `SystemMessage` inbox entry. Receipt identities include series, original occurrence date, actual start instant and offset; clearing the inbox cannot trigger duplicate delivery. A five-minute catch-up window collapses simultaneous due offsets for an occurrence into one alert. Claims also coordinate multiple tabs/devices. Each poll is bounded to twenty due occurrences.
- In-app reminders work while Sylf is running. Opt-in browser alerts use the existing non-caching service worker where available, with a Notification constructor fallback and permission/capability errors handled in settings. Browser notifications are grouped under one replacement tag. Polls retry with the regular timer, online and visibility wakes; transport timeouts prevent a hung request from stopping later checks. **There is no push subscription, cron delivery worker, OS alarm, or guaranteed delivery while the app/browser is suspended or closed.** Browser/OS behavior must be qualified on target devices before stronger delivery claims.
- Annotations retain their v1/v2 readers and serial recovery protocol. New recurring-item anchors can append `@<original occurrence date>` to the event identity to distinguish two occurrences on the same date. Existing anchors remain valid. Nested timeline scrolls remeasure anchors, and clipped item headings are excluded so marks are not drawn over a hidden event's former viewport position.
- Personal content saves refresh only the personal projection. Study data has a separate refresh owner and focus/visibility refreshes are coalesced. The month range is still shared across views. Reads use indexed overlap/series bounds and sparse exception ranges; no new scheduling dependency, paid AI parser, external provider, or duplicate event persistence was added. Quick add uses a deterministic local grammar and always opens an editable review, with defaults/uncertain interpretations explained.

Migration: `prisma/migrations/20261018010000_calendar_scheduling/migration.sql`, generated Prisma client, schema cache version **34**. New tables use the same backend-only RLS/privilege conventions as Phase 1.

## Extension boundaries

Version 1/2 notebook readers, semantic annotation anchors and serial note recovery remain canonical. Recognition is a reviewed derivative, never a replacement for editable ink. Membership is event-only. Neither shared nor connected commitments rewrite Planner capacity; study adjustments continue through the authoritative Planner review/apply flow. New ambiguous DST minutes choose the earlier occurrence; nonexistent minutes are rejected. Unchanged times retain their exact instants.

## Sylvie calendar assistance (Phase 4)

The existing floating Sylvie is the calendar assistant. The calendar publishes only transient navigation (selected date, view and visible range), validated as a hint on the existing authenticated chat route. Actual events, study commitments and notes are retrieved on demand through tools. No calendar history is attached to ordinary conversations and no separate AI interface, event store, endpoint or scheduling authority was introduced.

Seven tools extend the existing function-calling registry: `readCalendar`, `getCalendarEvent`, `findCalendarAvailability`, `readCalendarNotes`, `createCalendarEvent`, `updateCalendarEvent`, and `deleteCalendarEvent`. The last three use the existing signed proposal/confirmation flow and canonical personal calendar writes. They support event/time-block CRUD, explicit series/occurrence scope, recurrence and reminders. Local clock inputs resolve through the calendar's existing DST rules. Exact IDs, read revisions and original occurrence dates are preserved; creation and retries use stable server-generated command UUIDs. Confirmed acknowledgements invalidate the existing personal projection.

Reads cover at most 31 days, including expanded exceptions, date-based quests, deadlines, rest days and study history. Deterministic interval calculations report real overlaps, union booked time, free gaps and dated study effort. All-day commitments conservatively block a date. Default availability uses 08:00–20:00 and excludes rest days; custom windows are explicit. Historical study sessions do not become future reservations. Study overload means remaining dated effort exceeds free time in that window, and “heavily booked” means at least 85% occupied; neither replaces Planner capacity. Results disclose bounds/omissions. Date-associated note reads return at most eight bounded typed and reviewed recognition excerpts, never raw ink geometry. Phase 6 adds indexed notebook search across dates.

Calendar proposals are bound to the existing user/session/message signature and atomic claim. A schedule fingerprint is rechecked before confirmation; stale previews require a new read/proposal. Later user messages supersede older calendar previews. Batches check proposed event overlaps, reject competing edits to one series, and retain Sylvie's existing stop-on-first-failure semantics, rather than promising an atomic batch. Failed confirmations require inspecting current state before proposing again. The fingerprint is a bounded snapshot check, not a global lock against every other calendar writer. Series reviews state their 31-day horizon explicitly; they do not certify all future repeats.

Study generation/replanning still uses **Review in Planner**, including when calendar questions need a grounded recommendation first. Existing guarded quest tools remain available for explicit task requests, and linked-plan rejection explains the Planner review route. Personal events never directly reserve or rewrite Planner capacity. No unfinished Planner V2 functionality is enabled. Basic assistance is available without Advanced Options; optional workload presentation still uses existing account preferences. There are no proactive AI notifications or automatic schedule changes.

See [Phase 4 implementation, verification and handoff](reports/phase-4/report.md). Main owners: `lib/ai/sylvie/calendar-contracts.ts`, `calendar-tools.ts`, `turn-context.ts`, the existing chat executor/route, `lib/calendar/personal-service.ts`, and `lib/calendar/intelligence.ts`.

## Connected calendars (Phase 5)

Google Calendar and Outlook extend the existing event service, views and floating Sylvie through owner-scoped provider adapters, encrypted OAuth credentials, bounded caches and a durable conditional-write outbox. Apple/other public ICS subscriptions are read-only. Native events remain the default destination; provider controls live in Calendar settings → Connected calendars. Display visibility and inclusion in planning are independent. External reminders remain provider-managed. External events never become native/Planner records or a second recurrence authority.

`readUnifiedCalendarEvents` composes native and provider projections for display/intelligence; `readPersonalEvents` remains native-only for reminders. Incomplete/stale external coverage pauses free-time claims. The same signed Sylvie confirmations dispatch external changes, returning success only on provider acknowledgement and pending status otherwise. Schema cache version is **35**; migration `20261018020000_external_calendars` adds seven backend-only tables. Provider adapters and bounded worker live under `lib/calendar/external/`. Existing Planner authority is unchanged.

The implementation and mocked/isolated validation are in this checkout. Real provider-account qualification, deployment and a production scheduler remain required. See the [Phase 5 architecture and validation report](reports/phase-5/report.md) and [exact provider/deployment setup guide](reports/phase-5/setup.md). Phase 6 adds native event-only collaboration and optional local handwriting recognition below; external-account qualification remains postponed.


## Notebook intelligence and collaboration (Phase 6)

**Handwriting to text** is a contextual notebook disclosure. Selection uses the existing ink surface without changing strokes. Explicit recognition rasterizes selected pen lines locally and runs the pinned quantized TrOCR small English model in a short-lived WebAssembly worker. Up to six horizontal lines / 1,000 selected strokes are supported per run. The result is editable, copyable and can be appended to the typed note. Only reviewed, explicitly saved text becomes searchable. Mathematical notation, diagrams, multilingual recognition and raw-ink interpretation by Sylvie are unsupported. First use downloads roughly 80–90 MB including runtime/model data; later runs reuse browser caches where available. No handwriting is uploaded for recognition. Unsupported/slow/offline-first-use errors leave the notebook intact.

`CalendarNoteRecognition` stores bounded derived text, source stroke identities/hash, engine and its own revision. Saves lock the original note, validate its current revision and canonical stroke hash, and enforce 20 results / 16,000 text characters per note. Changed or removed selected ink invalidates its derived result; title/typed-text changes preserve valid recognition. Review drafts are device/owner/note scoped and cleared on logout. Search index triggers maintain a GIN-backed `tsvector` on the existing `CalendarNote`; no second notebook or copied ink document is indexed.

**Calendar settings → Advanced Options → Find in notebooks** searches private titles, typed content and reviewed recognition. Prefix keywords combine with inclusive civil date bounds and an optional recognized-only filter. `GET /api/calendar/notebooks` returns 20 excerpts with an opaque date/ID cursor; `?noteId=<UUID>` returns the owner's saved recognition. POST saves reviewed text, DELETE removes only a revision-matched derivative. Notes and recognition remain owner-only regardless of calendar memberships. Ranged calendar reads now return 240-character notebook previews plus a handwriting indicator; annotations retain the geometry needed for visible marks. Opening a notebook fetches its complete original document before mounting autosave, including when opened from search.

**Calendar settings → Shared calendars** creates event containers and manages exact-username invitations. Invitations must be accepted. Owners manage membership/name/deletion; accepted editors create/edit/delete shared events; viewers can read. Members may leave, owners may revoke. Shared events reuse `CalendarEvent`, recurrence exceptions, revisions, mutation IDs and recovery; `sharedCalendarId` is an explicit destination. Storage ownership stays with the calendar owner so leaving editors do not remove events. Every shared write locks its calendar and rechecks accepted edit permission; membership changes serialize on that same row. Browser database roles have no direct table privileges. No shared object relates to private notes, study history, Sylvie conversations, external connections or provider caches. Personal/default and provider calendars cannot be implicitly shared. Existing native reminder delivery remains personal-only; shared reminders are explicitly unsupported, with clear editor/service validation. No push or real-time editing system was added; visible shared projections refresh using the existing polling path.

`GET/POST /api/calendar/shared` uses cookie/revocation authentication, strict commands, ownership/role checks and no-store responses. Membership administration is revision checked. Limits: 10 owned calendars, 20 invited members per calendar, 40 active invited memberships and 50 catalog entries. Native event reads compose accepted shared calendars with private/provider projections; provider authority and Planner guards remain unchanged.

The existing Sylvie gains `searchCalendarNotes` (up to eight private excerpts) and shared destinations/roles in `getCalendarConnections`. Existing read/event/proposal tools understand shared metadata and permissions. Shared writes retain signed confirmation and disclose the destination to the user. Search uses bounded canonical services; no new assistant, model routing or AI backend exists.

Migration `20261018030000_calendar_completion`, generated Prisma client and schema cache version **36** are required. `npm run dev`, `npm run build` and mobile build scripts prepare the separate optional recognition worker/runtime through `scripts/build/build-calendar-recognition.mjs`; these generated assets must be deployed with `public/`. See [Phase 6 implementation, security, performance and final handoff](reports/phase-6/report.md). **The six implementation phases do not establish full production readiness: Phase 5 credentials, deployment/scheduler configuration and real Google/Outlook account tests remain mandatory.** Model-card licensing and physical stylus/WebView qualification are also recorded in that report.
