# Calendar Phase 5 — connected calendars

18 October 2026. Implementation in the existing Sylf checkout; **not yet qualified with real Google or Microsoft accounts, deployed as Phase 5, or connected to a production scheduler**. Missing provider-console access/credentials did not block implementation and mocked validation. Follow the [setup and real-account qualification guide](setup.md) before enabling the feature for production users.

## Delivered behavior

- Google Calendar delegated OAuth, account/calendar discovery, event reads and conditional create/edit/delete, recurring-series and individual-occurrence editing, provider reminders, incremental sync and notification receivers.
- Microsoft delegated authorization-code/PKCE flow, multiple account/calendar discovery, Graph event reads/writes, transaction IDs, reminders, recurrence and subscription receivers. Stable v1.0 delta is used for the default calendar. Other calendars use bounded paginated `calendarView` refreshes: specific-calendar delta is documented only in beta, which is not used.
- Read-only public HTTPS/webcal ICS subscriptions, including iCloud public calendar links. Expansion supports recurrence, exclusions, exceptions moved into the window, all-day dates and timezones through `ical.js`; no CalDAV passwords, Apple account login, feed writes or handwriting recognition were added.
- Existing month, week, day, agenda, daily workspace and optional timeline consume the same unified event DTOs. Connected-source names, permission indicators and subtle event styling distinguish sources. Native Sylf remains the creation default. A destination selector appears when writable connections exist. Read-only events offer details and an independent copy, with editing/deletion unavailable. External drag moves open the existing editor for review before a provider change.
- Connected calendars live inside existing Calendar settings, behind a disclosure. Accounts show permissions, errors, last sync, independent visibility/availability choices, refresh/reconnect/disconnect, sync and approved pending-operation retries. No new floating assistant, AI dashboard or main-calendar toolbar was introduced. Preference changes and connection records are owner-scoped, persistent across devices, and do not delete provider events or cancel provider reminders.
- Sylvie reuses existing routing, quota accounting, tool registry, signed confirmation and conversation infrastructure. `getCalendarConnections` supplies bounded provider/name-filtered calendar IDs and permissions. `readCalendar.calendarId` supports explicit source reads, including a hidden connected calendar. Existing create tools accept a destination; update/delete use provider ETags and explicit scope. Queued changes report pending; provider acknowledgement is required for success. Planner services, revisions and mutation guards remain authoritative and unchanged.

## Architecture and contracts

`lib/calendar/personal-service.ts` remains the composition owner. `readPersonalEvents` is still **native-only**, especially for existing reminder delivery. `readUnifiedCalendarEvents` merges native projections and external cache records for presentation and deterministic scheduling. Ordinary page rendering makes no provider HTTP call: slow or failing providers cannot hold the calendar render. A failed display cache returns native content with incomplete-coverage status. Strict planning reads fail rather than invent free slots when a planning-enabled calendar's requested coverage is missing or older than thirty minutes.

`CalendarEvent.external` carries calendar/provider identity, permissions, series/original occurrence metadata, provider ETag, busy/meeting flags, and visibility/planning preferences. All-day end dates stay exclusive. Timed instants stay UTC with IANA calendar/account context. Free/transparent events and calendars excluded from planning do not consume deterministic availability; hidden calendars still constrain planning when enabled. Visibility is a display choice, not a scheduling or deletion authority. Connected calendars continue background sync regardless of their display preferences.

New server-only modules under `lib/calendar/external/` separate credential security, fixed-host HTTP, OAuth/refresh, provider normalization, subscriptions, cache composition, durable writes, notifications and worker orchestration. Provider events never materialize as native events, quests or Planner reservations. Provider recurrence owns external occurrences; native recurrence is not a second expansion authority. Native copies are explicit user actions. Remote changes only update cached projections and never echo back as writes, preventing synchronization loops.

### HTTP surface

| Endpoint | Contract |
| --- | --- |
| `GET /api/calendar/connections` | Authenticated safe metadata/status; never credentials, feed URLs or cursors. |
| `POST /api/calendar/connections` | Strict owner-scoped connect, subscribe, disconnect, calendar visibility/planning, refresh, retry and sync commands. |
| `GET /api/calendar/connections/callback/{google,microsoft}` | Session-bound, expiring, one-use OAuth state plus encrypted PKCE; redirects to the configured calendar origin. |
| `POST /api/calendar/connections/notifications/{google,microsoft}` | Bounded provider notification validation; secret-checked notices only queue durable sync. Microsoft challenge returns bounded plain text. |
| `GET /api/cron/calendar-sync` | Existing `CRON_SECRET` bearer authorization; bounded durable-worker drain, independent of an open browser. |
| Existing `/api/calendar/personal` event writes | Optional `external: { calendarId, scope, etag }`, existing revision and stable mutation UUID. Dispatches to provider outbox. Native event/note contracts remain supported. |

External occurrences use their stable cached provider-event ID, not native `occurrenceDate`. Repeating external changes require occurrence/series scope; non-repeating changes use event scope. Whole-series reads retrieve the provider master and its ETag while retaining the selected cached occurrence ID for ownership. Unsupported repeat patterns/timezone encodings remain provider-owned: title/description edits can preserve them, while complex timing/rule edits are rejected with an actionable provider-edit instruction. Meeting changes disclose possible attendee notifications. Attendees, conferencing and unchanged provider-only fields/default reminders are omitted from PATCH rather than overwritten. Outlook supports one reminder per event; native and Google support their existing bounded sets.

### Sync and storage

The additive migration `20261018020000_external_calendars` creates seven backend-only tables. `CalendarConnection` stores an encrypted credential envelope and revision/refresh lease. `CalendarOAuthState` stores a state hash, signed-in-session hash and encrypted verifier. `ConnectedCalendar` owns preferences, permission/status, provider watches and calendar leases. `CalendarSyncWindow` owns fixed month cursors/checkpoints. `ExternalCalendarEvent` stores one small normalized event per calendar/provider ID. `CalendarSyncMember` links overlapping windows to that shared row; it does not duplicate event content. `ExternalCalendarMutation` records the exact approved operation before network writes.

Initial windows cover the current planning horizon and explicit browsed periods. Each calendar retains at most twelve requested/current-horizon month windows, with orphan cache records pruned. A window is capped at 2,000 occurrences and a displayed projection at 5,000 external events; excessive sets return a visible limit/coverage warning rather than silently certify availability. Historical browsing can refetch pruned cache. No years-long import is performed. OAuth states expire after ten minutes and are cleaned on connection starts/worker runs. Success receipts retain only hash, identity/result and minimal metadata until disconnect; full command and wire payloads are removed after success. Retaining the minimal receipt prevents an old device retry from recreating an event.

Provider cursors/next links are encrypted and checkpointed only when a page transaction commits. A multi-page initial scan is incomplete until its final page; the old generation is reconciled only at completion. Invalid/expired cursors clear coverage and restart without treating old data as free time. Delta cancellation removes relevant window memberships, including cancelled-series identities. Calendar-level leases and transaction fences prevent two workers from publishing competing cache generations. Token refresh uses a separate revision/lease so rotated credentials cannot resurrect a disconnected account. OAuth reconnection serializes the same account identity before binding ciphertext to its persisted row ID.

Google uses sync tokens; Graph's default calendar uses opaque fixed-window delta links; additional Graph calendars use paginated snapshots. ICS uses bounded, DNS-pinned TLS fetches and ETags when available; a feed without an HTTP ETag still requires a download but only its current window is expanded/persisted. Google/Graph steady polling targets five minutes; feeds thirty minutes. Notifications coalesce due timestamps, renewals are maintained, and bounded `after` drains speed up responses. The worker prioritizes approved operations, then due windows under a time budget with retry/backoff and `Retry-After`. Authentication revocation requires reconnection. Scheduler capacity/backlog determines actual latency; stale coverage is explicit. No paid integration or queue service was added.

### Provider write safety

Every accepted operation has an owner-scoped mutation UUID and immutable payload hash, persisted before a provider write. Schedule fingerprints also include connected-calendar busy/planning preferences, so changing availability choices invalidates an older Sylvie review. Local revisions and provider ETags reject stale edits; conditional requests carry `If-Match`. The exact wire patch is retained for interrupted operations. A lost PATCH response is reconciled against the provider's current desired fields; a lost DELETE response can succeed only after confirmed absence. A changed unrelated version does not authorize a second overwrite. Google creates use a stable client-supplied event ID; Graph creates use `transactionId`. A replay returns the receipt without another write. Conflicts/permanent errors require a fresh review; transient errors stay visibly pending for the same approved operation.

These are implemented safeguards with mocked provider coverage, not proof of all remote behavior. **Graph conditional-write enforcement, transaction-ID replay duration, account/tenant policy and DST require the real-account qualification in the setup guide.** No local lock can prevent every writer in another calendar app. A provider API that ignores a conditional header must not be considered safely qualified on that account.

## Security and deployment

Cookie authentication uses existing `getSession`, including revocation, plus resource ownership. Connections cannot provide arbitrary owners or scheduling authority. SQL enables RLS and revokes browser-role access on every new table. AES-256-GCM uses a required 32-byte server key, random nonce and record/purpose-bound authenticated data. OAuth includes one-use session state, PKCE, additional calendar consent and bounded connection attempts. Credentials never enter client imports or returned DTOs. The app uses existing Prisma/Supabase conventions; schema cache version is **35**, and Prisma generation passed.

Provider HTTP is limited to fixed HTTPS Google/Graph hosts and supported resources, with bounded bodies/timeouts and no redirect forwarding. ICS allows only public HTTPS/webcal destinations; it rejects literal/private addresses, embedded authentication and custom ports, validates every redirect, and pins the checked DNS address into the TLS connection to prevent rebinding. Feed links are encrypted, not returned to the browser or placed in provider error messages. Imported descriptions/titles remain untrusted text, not instructions or executable HTML.

Disconnect deletes only the selected external connection/cache/queued operations. It preserves provider events and every native Sylf event, notebook, quest, goal and Planner record. Google grant revocation is attempted after local deletion; remaining provider subscriptions expire and unrecognized notifications are ignored. Microsoft access can additionally be revoked in the account portal; the app does not invoke account-wide session revocation. Native reminder delivery never queries external projections, avoiding duplicate provider alarms.

The configured database received this additive migration successfully. A fresh local encryption key was written only to ignored `.env.local`; no provider secret was invented. TLS checks found `https://sylf-alium41rs-projects.vercel.app/` reachable with HTTP 200 and `https://sylf.app/` failing certificate validation as expired. No Phase 5 deployment, provider console configuration, or external scheduler was performed. [Setup](setup.md) gives exact variables, redirects, scopes and webhooks. Production needs valid HTTPS, secrets, the release deployment, a secured scheduler and real-account checks.

## Remaining qualification and Phase 6 handoff

- Real Google/Outlook authentication, token renewal/revocation, conditional-write behavior, external edits, provider recurrence exceptions, webhooks and closed-browser sync are **unverified** pending the setup guide. Live provider readiness is not claimed. Account credentials and console registrations cannot be supplied by repository code.
- Additional Outlook calendars deliberately use snapshot polling, not beta delta. Unsupported organization/shared-mailbox access, provider-specific advanced recurrence/timezones, attendee editing, conferencing controls and CalDAV writes are not simulated. Existing complex patterns can be read; unsupported timing/rule changes direct the user to the provider.
- The cron receiver and invocation script are implemented; an external scheduler is still required. Provider notifications have polling fallback. There is no unconditional freshness promise under provider outage, backlog, suspended hosting or an absent scheduler. Vercel Hobby's once-daily cron is insufficient; [Vercel's documented limits](https://vercel.com/docs/cron-jobs/usage-and-pricing) must guide deployment choice.
- Cache data is a projection. Preserve the external DTO/source identity and separate native reminder reader. Do not materialize provider recurrence through native recurrence or turn external appointments into Planner allocations. Keep CAS/ETag checks, outbox receipts, partial-failure language, signed Sylvie confirmation and owner/session boundaries.
- Phase 6 should extend existing v1/v2 notebook/ink readers and revision/recovery flows for any recognition feature, and design real membership/authorization before collaboration. Neither was begun here. Recognition must not replace original strokes. Monitor sync backlog/provider error rates and qualification results before increasing rollout.
